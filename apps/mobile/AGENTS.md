## Separate battery optimisation review

Every new Android feature — including any shared or cross-platform change that affects Android runtime behaviour — must receive a separate battery optimisation review before merge and release. This is a fresh, battery-focused reviewer task, distinct from implementation and from any functional or general code review. A general review does not satisfy this requirement, even if it mentions battery in passing. The existing Opus/Sol pipeline otherwise stays unchanged: Sol handles operations and coordination, Opus writes source code and carries out code review, and Muse writes deliverable prose. Delegate the battery code review to a fresh Opus task.

Review the whole feature's runtime behaviour, not only the changed lines. Cover foreground, background and idle behaviour; lifecycle and cancellation; wake locks; jobs, WorkManager and alarm scheduling; polling intervals; retries and backoff; network batching; sensors, location and listeners; CPU use and unnecessary services; and behaviour under Doze and battery saver. Prefer work that stops when it is no longer needed, runs at the lowest useful frequency, and batches or defers non-urgent work.

Battery efficiency must not break essential reliability, including alarms and other time-critical behaviour the user depends on. Where efficiency and reliability conflict, state the trade-off and justify the decision. Do not use a blanket battery optimisation exemption as a substitute for efficient design; request an exemption only where it is genuinely required for core reliability, and still minimise background work.

Record the review in the pull request: findings, fixes made or justified decisions, checks or measurements carried out, any limitations, and a final explicit verdict. Resolve all actionable findings before merge, and re-review any changes made in response. Keep measurement proportionate to the risk — lightweight checks for small or low-risk changes, device measurement where background, scheduled or always-on work is involved. Never invent test or measurement claims. If device evidence is unavailable, say so plainly in the pull request and record what was checked instead.
